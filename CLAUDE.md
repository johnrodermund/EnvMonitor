# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ESP32 Arduino sketch that logs pH, electrical conductivity and water temperature, and serves a Preact web app over Wi-Fi. All firmware is in `esp32_res_copy_largebox.ino`; the web app source is in `web/` and is embedded in the firmware as `src/web_assets.h`. `data/` is the LittleFS image, which now holds only seed state files (no web pages).

## Build and verify

Run tests on the host with `pio test -e native` (add `-f test_ring_stats` for one suite, `-v` for per-test results). This needs a C++ compiler on PATH. Tests in `test/` cover Arduino-free code in `src/`; keep logic there to make it testable. Frontend tests run with `npm test` in `web/`.

Before every firmware build run `npm run build && npm run embed` in `web/` (Node 26). It gzips `web/dist/` into `src/web_assets.h`, which the sketch serves, and commit the regenerated header. The embed script fails if the gzipped app passes 60 KB (61440 bytes); the current app is about 41 KB. `npm run dev` serves the app against `web/mock/`.

There's no firmware build config or linter, and the board and library versions aren't recorded. Compile with the Arduino toolchain for ESP32. The device has run a build for `lolin_c3_mini` (Arduino core 2.0.14; the board itself is an unconfirmed guess, only the ESP32-C3 chip is certain) with flags `-DARDUINO_USB_MODE=1 -DARDUINO_USB_CDC_ON_BOOT=1`, and libraries `mathieucarbou/ESPAsyncWebServer`, `matmunk/DS18B20` and `paulstoffregen/OneWire`.

Pinout: DS18B20 on GPIO 8, relay on GPIO 1, pH and EC on GPIO 3 (`sensorPin`). The box was laid out for a D1 mini, so GPIO 3 sits in its A0 position; GPIO 0 is unconnected. Code must not use `A0`, which means GPIO 0 on this board.

- The sketch name doesn't match its folder (`EnvMonitor`). Arduino tools require them to match, so copy or rename before compiling.
- The site is part of the firmware, so a firmware upload (OTA works) updates it. A LittleFS upload of `data/` is needed only for first-time seeding; never do it on a live device. Uploading `data/` replaces the device filesystem, which wipes logged readings, calibration, title and interval with the seed files in `data/`.
- Real verification needs the hardware. If it isn't available, say the change is untested.

## Architecture

Three execution contexts share globals. Five FreeRTOS mutexes guard the shared state the handlers touch (see Locks below):

- `loop()` services OTA and the settle test, then runs at most one slow step per pass, in this order: the readings API upload, the events save, one event sync, the pending settings write, one Pi fetch. Then it yields. It skips the slow steps entirely while a probe is warming up or sampling, or a settle test runs, so Wi-Fi traffic stays off the ADC. It then yields with `delay(2)`. The ESP32-C3 has one core and `loop()` runs at a higher priority than `loop2()`, so without that yield sampling starves and a reading takes minutes.
- `loop2()`, a FreeRTOS task, calls `ReadingCycle::tick()`, which does all sensor work.
- `AsyncWebServer` handlers use only `request()`, `status()` and read accessors on the cycle. Keep slow work out of handlers: they copy data under a lock or queue work for `loop()`, and `loop()` runs at most one slow step per pass (an API upload, an events save, an event sync, a settings write or a Pi fetch).

`ReadingCycle` in `src/reading_cycle.h` owns every reading, calibration and restart transition. Its `CycleHost` interface has two adapters: `DeviceHost` in the sketch and `FakeHost` in the tests. A new command interrupts whatever is running, and an interrupted reading records nothing. pH and EC share one analog input (GPIO 3), and the relay selects which sensor is powered: on for pH during warmup and sampling, off for EC. The user wants the pH board powered as little as possible (it wears the probe), while EC can stay on, so the relay rests on EC between readings.

pH timing (`src/ph_sampling.h`): a water pump in the tank puts mains hum on the pH electrode, and reads exactly 100 ms apart alias 60 Hz into a random per-reading offset. All pH reads (warmup and sampling) run on one fixed 105 ms grid, so each 20-read window spans whole 60 Hz and 50 Hz cycles and the hum averages out; EC reads are 105 ms apart for the same reason. The warmup is a fixed 30 s. The settle test showed the board drifting along the same curve every time, within ~0.07 pH of its plateau at 30 s and on it by ~60 s; the user chose 30 s to limit probe power. A rule that waited for two close window means was tried and dropped, because it fired at varying points of the steep part and moved readings ~0.08 pH. Calibration uses the same warmup, so recalibrate after changing it. A reading is the trimmed mean of 20 samples (2 lowest and 2 highest dropped). The last warmup's length and its 2.1 s window means show in `/diag` (the length also in `/api/status`). The settle test powers pH for 3 minutes, logs hum-free window means, marks where readings start sampling and ends with 200 reads 1 ms apart that show the hum. Calibrate and Measure hold sampling, and a hold abandoned for 15 minutes resumes it and discards any unfinished calibration.

Web app and API: `web/` is a Preact single-page app with hash routes (Dashboard, Charts, Events, Measure, Calibrate, Settings, Appearance, Diagnostics). On a phone the nav is one scrolling row. `/` and `/assets/*` are served gzipped from `src/web_assets.h` with an ETag (304 on `If-None-Match`; `index.html` is `no-cache`). The JSON API: `GET /api/status`, `/api/readings`, `/api/settings`, `/api/pi`, `/api/ranges`, `/api/apiconfig`, `/api/events`, plus `POST /api/settings`, `/api/events`, `/api/command` (`cmd=reading|measure_start|measure|calibrate_start|calibrate_ph4|calibrate_ph7|cancel|restart|reset`), `/api/ranges`, `/api/apiconfig` and `DELETE /api/ranges`. POST bodies are form-encoded, not JSON, and ranges are saved by `POST` (not `PUT`) with flat fields such as `ph_valid_lo`. `/api/apiconfig` reports `token_set`, never the token. The plain-text `/diag` and `/apiconfig` pages remain for troubleshooting. JSON builders live in `src/api_json.h`, command dispatch in `src/api_commands.h`.

EC temperature compensation: the reading log and `/readings.txt` keep raw EC. Everything that leaves the log refers it to 25 °C with `ecAt25()` (`src/sensor_math.h`, EC₂₅ = EC ÷ (1 + coef/100 × (°C − 25)), converting the DS18B20's °F): `/api/readings`, the `/api/status` EC value, mean and std (`compensatedEcStats()`), the manual reading, event detection and the readings upload's `ec`. `ec_adc` stays raw, so the Pi can always recompute. A changed coefficient therefore re-applies to the whole on-device history with no step for the detector to mistake for a top-up, but readings already uploaded keep the value they were sent with. The coefficient (% per °C, 0–5, 0 = raw, default 2.0) is `ec_temp_coef` in `/api/settings` and `/api/status`, saved in NVS namespace `sensor`, key `ec_coef`. A missing or implausible temperature (outside 0–50 °C) leaves EC raw. `tools/ec_temp_coef.py` suggests a coefficient from the Pi's database: it recomputes raw EC from `ec_adc`, splits the data at top-ups and gaps, detrends EC and temperature per segment, and fits the pooled slope. Fitting hour-to-hour changes instead underestimates it, because hourly temperature changes are about one DS18B20 step.

Appearance: theme (system/light/dark), accent colour, text size, temperature unit, time format, the Charts page's starting window and whether Dashboard tiles show their average and trend lines. They're saved on the device so every browser shows the same: `src/appearance.h` validates them and stores them as one `key=value;...` string in NVS namespace `ui`, key `appearance`, read and written as flat fields of `/api/settings`. The app applies theme, accent and text size as `data-theme`, `data-accent` and `data-text` on `<html>` (CSS tokens in `styles.css`), and caches the last look in `localStorage` only to avoid a flash on load. The °C option is display only: the device logs and uploads °F, and ranges stay in °F.

Pi cache: `PiCache` (`src/pi_cache.h`) holds the last replies from the Pi's `/stats?window=24h`, `/reports/latest` and `/thresholds`. `loop()` fetches one endpoint per pass, one round every 5 minutes, and `/api/pi` serves the cache with each entry's age and last error. Replies over the per-endpoint body cap are refused unread. The dashboard review panel and trend lines come from this cache, so they work with the Pi down but show age and "unreachable".

Device ranges: colour ranges come from the Pi's thresholds by default. `POST /api/ranges` stores device ranges in NVS (namespace `ranges`, key `json`), which override the Pi's for the page only; `DELETE /api/ranges` ("Use Pi ranges") removes them. `/api/ranges` reports the source (`device`, `pi` or `builtin`). Device ranges never reach the Pi.

Tank events: top-ups and feedings, detected or logged by the owner (spec: PiServer `docs/superpowers/specs/2026-11-15-tank-events-design.md`). After each recorded reading, `detectEvents()` in the sketch converts the reading log's local timestamps to UTC with `mktime`, runs `detectAt()` (`src/event_detect.h`, the same rule as PiServer `agent/events.py`) over the last 12, passes the result through `CandidateHold` (a step crosses the threshold over several windows; the hold keeps the strongest and releases it once 3 later windows haven't beaten it, so a suggestion appears about 1.5 hours after the step, in its final form), and offers it to `EventLog<100>` (`src/event_log.h`), which applies the 2-hour rules and fills before/after medians of events that lack them. Detected events can be rejected, never deleted; deleting a manual event keeps a tombstone until its delete syncs. `POST /api/events` (form `op=create|update|delete|reject|confirm`, `seq`, `kind`, `detail`, `occurred_at` as ISO with a zone, `note`, `status`; logic in `src/event_api.h`) changes RAM only. `loop()` saves `/events.txt` and PUTs one dirty event per pass to `<url>/events/<uid>` (`src/event_sync.h`), sharing the readings upload's backoff and token. An event changed while its PUT is in flight stays dirty (generation counter). A 400 or 422 marks that version `refused`: it isn't resent, the app shows "refused by the Pi" instead of backed up, and the next edit retries. The seq high-water mark is also kept in NVS (`events`/`next_seq`, written before `/events.txt`), so a lost or re-seeded file never reuses a uid on the Pi. `GET /api/events` stops at 32 KB, newest first, with `"truncated":true` when older events were left out: the web server copies the reply again and a failed allocation reboots the C3. Nothing is stamped or synced before NTP sync, and an event whose `updated_at` is over a day ahead isn't synced (`clock_ahead` in `/api/status`). Unsaved edits are lost on a reboot; saved, unsynced ones come back dirty. Detection settings (`topup_min_drop`, `feeding_min_rise`, `feeding_enabled`) go through `/api/settings` and live in NVS namespace `events` (keys `topup_drop`, `feed_rise`, `feed_on`: NVS keys are at most 15 characters). `LittleFsStore` writes each file through its own `<path>.tmp`, since readings and events can be saved at once.

pH swings (spec: `docs/superpowers/specs/2026-11-16-ph-swing-design.md`): `detectSwings()`, called at the end of `detectEvents()`, works on the same reading-log copy with local day and minute from the log timestamps. At the first reading from 01:30 local it records the day just ended as a `ph_swing` event (detected, confirmed): the swing of the median-of-3 smoothed pH, the biggest 1-hour rise and fall with their times and offsets from the light changes, and the jitter (median change between consecutive readings), in the note. About 2 hours after each lights-on and lights-off change it judges that change (`src/ph_swing.h`): the largest 1-hour change starting from 30 minutes before to 60 minutes after it, and the jitter over the last 12 hours. With at least 5 past values, a jump or jitter above `swing_alert_factor` times the median of the last 14 (lights-on and lights-off jumps kept apart) makes a suggested `buffer` event when the 12-hour median EC is above `nutrients_ok_ec`, else a suggested `nutrients` event; none within 2 days of a buffer, nutrients or water change event that isn't rejected. A day or window under 75 % of its expected readings is skipped, so the day record needs a reading interval of 6 minutes or more (the 200-reading log must hold 75 % of a day). Waiting until 01:30 lets a change starting before midnight have its hour. At most one suggestion is added per 24 hours, rejected or not (`last_sug`). Water temperature outside the active target range (the Dashboard's: device, Pi or built-in) on every reading for 2 hours (with 75 % of the expected readings, so not one reading after a gap) adds one suggested `other` event; it re-arms after an hour back in range (RAM only). Records that aren't steps (`EventLog::addDetected()`) never block top-up detection, and `fillDeltas` leaves events that already carry pH values alone. Settings `lights_on`, `lights_off` (local `HH:MM`), `nutrients_ok_ec` (0–5000, default 275) and `swing_alert_factor` (1.1–5, default 1.5) go through `/api/settings`. They, the histories and the last day and light change processed live under `settingsLock` and in NVS namespace `swing` (keys `lights` as on×1440+off, `ok_ec`, `factor`, `history`, `last_day`, `last_chg`, `last_sug`), saved by `loop()` as one more pending-settings item. The Pi must accept the `ph_swing` and `nutrients` kinds (PiServer `event-kinds`), or it refuses those events with 422.

Locks: `settingsLock` (title, interval, detection limits, swing settings and state, and their pending-save flags), `readingsLock` (`readings` and `lastPhUncertainty`), `eventsLock` (`events` and `eventsSavePending`), `piCacheLock` and `apiQueueLock`. Take them with `portMAX_DELAY`, hold them only to copy data, and never do I/O while holding one. The reading save follows this: `DeviceHost::recordReading()` and `wipeReadings()` build the file text with `ReadingLog::saveText()` under `readingsLock`, release it, then write it through `LittleFsStore`. Device ranges live in a RAM copy under `settingsLock` (loaded once at boot), so `GET /api/ranges` never opens NVS.

`ReadingLog` in `src/reading_log.h` takes one complete reading at a time, so its series stay aligned, and it saves all 200 entries to `/readings.txt` through a store adapter. Boot replays that file's rows to rebuild statistics. If the file is missing, it migrates the old `/phdata.txt`, `/ecdata.txt`, `/wtdata.txt` and `/datetime.txt` files, which is the only remaining use of `src/stats_file.h`.

Readings API upload: `DeviceHost::recordReading()` only queues each finished reading in `apiQueue` (`ReadingQueue` in `src/reading_queue.h`, 24 entries, under `apiQueueLock`). `sendQueuedReading()` in `loop()` POSTs the oldest one as JSON to `<url>/readings`, with 3 s timeouts and a 10 s to 5 min backoff. A 200 or 201 removes it, a 400 or 422 drops it as never acceptable, and anything else keeps it for a retry. When full, the queue drops its oldest reading. Readings taken before NTP sync aren't queued, because their timestamp would be wrong. The URL, token and device name live in NVS (`Preferences` namespace `api`), set by a POST to `/api/apiconfig` or the legacy `/apiconfig` (form fields `url`, `token`, `device`). A GET of either, or `/diag`, shows the status but never the token. The API itself runs on the Raspberry Pi and isn't in this repo.

Charts use uPlot, bundled into the app, so the viewing browser needs no internet access.

## Gotchas

- `setup()` resets `interval0` to 10 minutes if it's outside 120000–43200000 ms (2 minutes to 12 hours), matching the 2–720 minute range of `POST /api/settings`.
- `writeFile()` blocks for 2 s per file. It's used for settings, always from `loop()`; readings go through `LittleFsStore`.
- If `LittleFS.begin()` fails, `setup()` returns early, leaving no web server, OTA or sampling task.
- `ph4` and `ph7` hold raw ADC readings for the two-point calibration, not pH values.
- NTP settings and UTC offset are hardcoded at the top of the sketch.
- Wi-Fi credentials live in NVS (`Preferences` namespace `wifi`), not in source or `data/`. With none saved, or if the saved network fails at boot, `runWifiSetupPortal()` opens the `EnvMonitor-Setup` access point at 192.168.4.1. It restarts after a save, or after 5 minutes if a network is saved. No sampling or OTA runs during the portal.
