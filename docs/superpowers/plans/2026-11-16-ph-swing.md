# pH Swing Tracking Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The device records a daily pH swing event, suggests buffer or nutrients when pH jumps more than usual at a light change or reads erratically, and warns when water temperature stays out of range.

**Architecture:**
- A new host-tested header, `src/ph_swing.h`, holds the day metrics, the light-change judgement, the 14-value histories, the suggestion rule, the temperature watch and the settings parsing.
- `EventLog` gains two kinds and a generic `addDetected()`.
- The sketch feeds these from the reading-log copy `detectEvents()` already makes, and saves the swing state from `loop()`.
- PiServer accepts the two new kinds.

**Tech Stack:** ESP32-C3 Arduino core 2.0.14, FreeRTOS, NVS `Preferences`, PlatformIO Unity host tests, Preact and Vitest, FastAPI and pytest (PiServer).

**Spec:** `docs/superpowers/specs/2026-11-16-ph-swing-design.md`

## Global Constraints

- Follow EnvMonitor `CLAUDE.md`:
  - Take locks with `portMAX_DELAY`, hold them only to copy data, and never do I/O under a lock.
  - Run one slow step per `loop()` pass.
  - Keep logic in `src/` with host tests.
  - Run `npm run build && npm run embed` before a firmware build.
  - Never upload `data/`.
- New kinds: `ph_swing` and `nutrients`. `detail` stays empty for both.
- Settings defaults:
  - `lights_on` `07:00` and `lights_off` `19:00` (local `HH:MM`)
  - `nutrients_ok_ec` 275 (µS/cm as the app shows it)
  - `swing_alert_factor` 1.5
- 75 % coverage rule: a day or a window needs at least 75 % of its expected readings (span ÷ interval).
- Smoothing: pH median of 3 consecutive readings. A 1-hour change runs from a reading to the first reading at least 3600 s later.
- History: 14 values each for the lights-on jump, the lights-off jump and the jitter. At least 5 past values before a trigger.
- Quiet period: no suggestion within 2 days (172800 s) after a `buffer`, `nutrients` or `water_change` event that isn't rejected or deleted.
- Temperature warning: fires after 2 h with every reading out of range on either side; re-arms after 1 h with every reading back in range. The state lives in RAM.
- Notes are at most 200 characters.
- The PiServer change must be deployed before the device firmware is flashed. Deploying needs the owner's OK.

## Review Focus

1. **A lights-off change near midnight under 16/8 (for example 23:30).** Expect: it's judged about 2 hours later, from readings that cross midnight. Neither the day record nor the judgement skips it. (Task 2 test `change_window_may_cross_midnight`.)
2. **The device reboots after a light change was judged.** Expect: the same change isn't judged again, because its key is saved. (Task 5 saves `last_change`; Task 2 test `same_change_has_same_key`.)
3. **The light schedule changes mid-day (12/12 to 16/8).** Expect: no crash and no double judgement. A change that hasn't happened yet under the new schedule isn't judged early. (Task 2 test `change_not_judged_before_its_window_ends`.)
4. **Missing readings (device off, Wi-Fi portal).** Expect: the day or window is skipped by the 75 % rule; no event is made from a handful of readings. (Task 2 tests `day_under_coverage_is_skipped` and `window_under_coverage_is_skipped`.)
5. **Long notes.** Expect: every generated note fits 200 characters with the largest realistic numbers. (Task 3 test `notes_fit_200_characters`.)

### Task 2: Day metrics and the light-change judgement

**Files:**
- Create: `src/ph_swing.h`
- Test: `test/test_ph_swing/test_main.cpp`

**Interfaces:**
- Produces:
  - `struct SwingSample { long long epoch; int localDay; int localMinute; float ph; float ec; float wtF; };`
    - `localDay` is `yyyymmdd`; `localMinute` is 0–1439.
    - Samples run oldest first, and only clock-set readings are included.
  - `struct LightSchedule { int onMinute = 420; int offMinute = 1140; };`
  - `struct DayMetrics { bool ok; int day; float swing, phMin, phMax, riseSize, fallSize, jitter; long long riseAt, fallAt, bigAt; float bigBefore, bigAfter; };`
    - `bigAt`, `bigBefore` and `bigAfter` describe the larger of the rise and the fall.
  - `DayMetrics dayMetrics(const SwingSample *s, int n, int day, int intervalMin);`
  - `struct ChangeJudgement { bool ok; bool lightsOn; int key; long long changeAt, jumpAt; float jump, jumpBefore, jumpAfter, jitter, ecMedian; };`
    - `key` = `localDay * 2 + (lightsOn ? 1 : 0)`.
  - `ChangeJudgement judgeLatestChange(const SwingSample *s, int n, const LightSchedule &l, int intervalMin);`
    - The latest lights-on or lights-off change whose window has ended by the newest sample.
    - The window starts 30 min before the change. 1-hour changes start between change − 30 min and change + 60 min, so the window ends at change + 120 min.
    - `jitter` and `ecMedian` cover the 12 hours before the newest sample.
    - The change epoch is derived from a sample of that local day: `sample.epoch + (changeMinute − sample.localMinute) × 60`.
    - `ok` is false when no change qualifies, or when the window has under 75 % coverage.

  - `class TempWatch { bool check(const long long *epochs, const float *tempF, int n, float lo, float hi, std::string &note, long long &at); };`

### Task 5: Sketch wiring, settings and docs

**Files:**
- Modify: `esp32_res_copy_largebox.ino`, `src/api_json.h` (`settingsJson` gains `const LightSchedule&, const SwingLimits&`), `test/test_api_json/test_main.cpp`, `CLAUDE.md`

**Behaviour:**
- **Globals under `settingsLock`:**
  - `lightSchedule` and `swingLimits`
  - `swingHistory`, `lastSwingDay` and `lastChangeKey`
  - `hasPendingSwing`: `loop()` saves NVS namespace `swing` (keys `lights`, `ok_ec`, `factor`, `history`, `last_day`, `last_chg`) as one more pending-settings item.
- **`detectEvents()`** builds `SwingSample`s beside `detectSamples`: the `LogTime` gives `localDay` and `localMinute`, EC is compensated, and temperature comes from the log. Then:
  1. **Day record:** when the newest sample's `localDay` differs from the previous sample's and the previous day isn't `lastSwingDay`, run `dayMetrics` for that day. If it's ok, `addDetected("ph_swing", "confirmed", m.bigAt, swingNote(...), m.bigBefore, m.bigAfter, now)`, then set `lastSwingDay` and mark the state pending.
  2. **Change judgement:** call `judgeLatestChange`. If it's ok and its key isn't `lastChangeKey`:
     - Call `judgeSuggestion` with the history.
     - If a suggestion is found and `!events.recentFix(now, 172800)`, call `addDetected(kind, "suggested", s.at, s.note, j.jumpBefore, j.jumpAfter, now)`.
     - Then `recordJudgement`, set `lastChangeKey`, and mark the state pending.
  3. **Temperature:** a static `TempWatch` checks against the active temperature target. Extract `Ranges activeRanges()` from `rangesText()` and reuse it. On a warning, call `addDetected("other", "suggested", at, note, NAN, NAN, now)`.
- **Locking:** each event change happens under `eventsLock` and sets `eventsSavePending`. The settings and swing state are copied in and out under `settingsLock`.
- **`/api/settings`:** GET adds the four fields. POST accepts them through `applySwingSettings`. They count toward the "nothing to save" check.
- **CLAUDE.md:** a pH swing paragraph, the settings, the NVS keys, and the note that detection needs a reading interval of 13 minutes or less to see a full day.
